# 一条能力的三个归宿：**库 / 生成器 / 应用**（`interest/yi` 迁移实战总结，2026-10-23）

> 这份文档回答一个问题：**同一件事，什么时候该写进库、什么时候该由生成器决定、
> 什么时候只能是应用自己的代码？** 判据不是偏好，是三条可验证的事实。

## 0. 一句话规则

```
库    ：机制 —— 不依赖任何源项目、对所有应用都成立、能由"类型 + 一条断言"守住的东西
生成器：语义 —— 只有它手上有源项目（CSS、选择器、祖先链），因此只有它能判断"应该是什么"
应用  ：意图 —— 源项目特有的业务含义，机械迁移**注定**认不出来，只能人写
```

检验一条边界划得对不对，问三个问题（顺序不能反）：

1. **它在源码里有没有答案？** 有 ⇒ 生成器。没有 ⇒ 后两级。
2. **它对**所有**应用都成立吗？** 成立 ⇒ 库。只对这个应用成立 ⇒ 应用。
3. **认错了会不会静默出错？** 会 ⇒ 宁可**点名**（进迁移报告的 TODO），不要猜。

## 1. 入库的东西（`render.mbt` / `style/` / `moobile-host/*.js` 的宿主侧）

**判据：与源项目无关，且"不做就是错的"。**

| 能力 | 落点 | 为什么是库 |
|---|---|---|
| 文字默认样式 + **最近一层文字上下文** | `render.mbt`：`set_text_style` / `TextRef.near` | RN 里没有 CSS 继承，而 `react-native-web` 给每个 `Text` 附了一条 `-apple-system` 默认规则 ⇒ **不显式落就必然错**，与源项目无关 |
| `make_element` 的上下文进出（先设上下文、再画孩子） | `render.mbt` | 顺序本身是机制（样式由父元素决定），孩子必须收成 thunk |
| 文本键白名单（`is_text_key`） | `render.mbt` | "哪些属性会继承"是 CSS 常识，**一处定义**，别处不许重复 |
| 能力注册与宿主契约 | `moobile-host/core.js`、`hosts/` | 应用不该关心平台差异 |
| 迁移后的**自查**规则（`page-style-unused` / `no-native-scroll`） | `moobile-host/lib/migrate/app-audit.js` | 两侧都只在原生上现形；判据写在库里，指南就不再是口口相传 |

⚠️ 反例（**不要**放进库）：
- "沿祖先链按 CSS 规则合成样式" —— 库**没有**源 CSS 的祖先链，只能猜。实测猜错两次（见 `FINDINGS.md` 十六续）；
- 具体列宽、具体字体名 —— 那是源项目的事实，不是机制。

## 2. 进生成器的东西（`npm/moobile-host/lib/migrate/`）

**判据：需要源项目的信息才能做对，且规则对所有源项目通用。**

| 能力 | 落点 | 为什么是生成器 |
|---|---|---|
| CSS 声明 → `@style` 调用的**逐条映射** | `style-map.js` | 只有它看得见 CSS |
| **语义修正**：`line-height` 无单位 = 倍数（RN 是点数） | `style-map.js` | 两边语义不同，**只有知道源 CSS 的人能判** |
| **降级策略**：`display:grid` → `flex(row)+wrap`，列宽写子项 | `style-map.js` + `style-emit.js` | 需要"容器 + 子项"两半信息 |
| **祖先链展开**（`.a .b > .c` 落到哪个用法上） | `style-emit.js`（`sites[].chain`） | 只有源码里有这条链 |
| **认不出就点名**（`grid-items-unknown` → `MIGRATION.md §2.2b`） | `style-emit.js` + `create.js` | 生成器**知道**自己认不出什么，这个"知道"必须变成产物的一部分 |
| 生成物与磁盘的**逐函数同步判据** | `lib/migrate/regen-diff.js` + `tools/regen_styles_check.mjs` | 生成器的产出必须能被"重算一遍"验证 |
| 应用目录的结构与入口改写 | `create.js` / `class-rewrite.js` | 机械改写，机械可验 |

⚠️ 边界上的两条经验：
- **`@media` 里的值不算**：源 CSS 在窄屏把列宽从 116 改成 96，生成器只能取"无媒体查询"那一份，
  窄屏那条**照旧进 `ruleLosses` 点名**（RN 没有媒体查询，断点要在 Model 里表达）；
- **精度不足的规则不进生成器**：我试过"凡祖先链为空的用法都算网格子项"，实测空链有 8 条、
  只有 1 条该算（**精度 1/8**）⇒ 删掉，改成点名。

## 3. 只能是应用自己的东西（`examples/apps/<app>/`）

**判据：源项目的意图，机械迁移注定认不出来。**

| 东西 | 落点 | 为什么只能是它 |
|---|---|---|
| 触发 `set_text_style_of(@styles.page())` | `main.mbt` 的 `init_app` | 库提供机制，**调用点**是应用的决定（写在哪一帧、要不要） |
| 卦卡属于哪个网格容器 | 视图代码（人写） | 源码里是 `let card = …` + `shang.push(card)` —— **书写形状里没有父子关系** |
| `@media` 断点 → Model 里的响应式 | `main.mbt`（`@sub.on_resize`） | 断点是设计决策 |
| 折叠开合、变爻、错综互导航这些**状态** | `main.mbt` 的 Model/Msg | 业务语义 |
| **判据本身**（这个应用该满足什么） | `verify.mjs` | 判据要写在"用户看得见的层"上，只有这个应用知道那是什么 |
| 生成物被手改的部分 | `styles.mbt`（**要能查出来**） | 允许改，但必须能被 `regen --styles --diff` 抓出来 |

⚠️ 三条硬规矩：
- **生成物不许默默漂移**：`styles.mbt` 允许人改，但 `tools/regen_styles_check.mjs` 必须能
  逐函数报出"哪些是人改的"（判据含证伪：人工改一格 + 加一格必须被抓住）；
- **判据不许量实现**：这一轮我在"卦卡几列"上连踩四个口径坑（找 `min-width`、找 `flex-flow`
  字面量、混算多个容器、用只命中 1 个结果的搜索词）。最后落到**纯几何**（按 y 分行数每行几张）
  —— 与降级怎么实现无关；
- **应用的 `main.mbt` 要能被重生成**：手改是允许的，但改动要小、要有注释说明为什么。

## 4. 分工的形状（一张图）

```
源项目(CSS + rabbita 视图)
      │
      │  ①生成器：读源码 → 语义（选择器匹配、祖先链、单位语义、降级策略、认不出的点名）
      ▼
  styles.mbt + 改写后的视图 + MIGRATION.md（含"要人看一眼"的清单）
      │
      │  ②库：机制（渲染期的上下文、继承落点、能力注册、自查规则）
      ▼
   三端产物（web / android / 桌面）
      │
      │  ③应用：意图（调用点、业务语义、断点、判据）
      ▼
   验收
```

**三者的接口只有三样**：`@style.Style`（生成物 → 库）、`set_text_style_of`（应用 → 库）、
`MIGRATION.md` 的 TODO 清单（生成器 → 人）。

## 5. 下一轮按这张表怎么落

| 待办 | 归宿 | 为什么 |
|---|---|---|
| 逐元素**字号**（`Text` 上的 `font-size` 落到字上） | **库**（补"最近一层"已有，缺的是"跨 `View` 的判别"）+ **生成器**（把静态可算的字号固化成字面量） | 库不知道 `View` 该不该断继承，生成器知道 |
| `@media` 断点 | **应用**（Model 里按窗口宽度）+ **生成器**（点名，别静默丢） | 断点是设计决策 |
| 观感（字号层级 / 留白 / 信息架构） | **生成器**（字号来自 CSS）+ **应用**（层级与节奏是设计） | 两者都要 |
