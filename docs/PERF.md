## 0. 一句话结论

**一个 1000 行的非虚拟化列表，光"翻译成 React 元素"就曾要 ~12.6 ms/帧**（当前树 7.6 ms
—— 60fps 的预算是 16.7 ms **全部**，而这还不含 React 的 diff/commit、不含布局、不含原生渲染）。

**其中最大的一笔已经修掉了**：`Props` 的四张属性表原本在**每个元素每帧**被整份复制
（`resolve_attrs` → `Attrs::copy` → `Props::copy`）。先用**消融探针**量出这笔值 **28%~36%**（§7.3），
再把四张表换成**不可变结构** ⇒ "复制"退化成 **O(1) 指针拷贝**，实测
**−32.4%（N=1000）/ −29.3%（N=5000）**，两组各 9 次 `min` 的区间**完全不重叠**，
而且**公开契约一点没破**（复制这个动作还在，只是变便宜了）。做法与全部数字见 §8。

| 阶段 | N=1000 每帧 `min` 统计量 | 会话内变化 |
|---|---|---|
| D3 之前（首刀） | 12.64 ms | — |
| D3（标签表索引化，§4） | 11.68 ms | −7.6% |
| **P1（属性表改不可变，§8）** | **11.20 → 7.57 ms** | **−32.4%** |

⚠️ 这张表**跨了两个会话**（同一份产物跨会话能差 4~7%，§5.3）⇒ **只有同一行内的变化可比**，
**绝对值不要跨行相减**（每一行都是当时同一会话里的对照）。

**两次归因都改写过读代码的结论**（被推翻的说法都在本文件里标注保留）：

| 读代码时的说法 | 实测 |
|---|---|
| "`Props.styles` 是**不可变 HAMT**，`styles_map()` 读的时候又 `copy_map` 一次" | ❌ **两处都错**：`Map` 是**可变** LinkedHashMap；`styles_map()` 是**只读访问器，不复制**。复制的真身是 `Props::copy`（四张表），由 `resolve_attrs` **每元素**触发 |
| "下一刀 = 去掉 `styles_map()` 那次复制" | ❌ **瞄错了，而且奖池小**：那一刀最多值 −5.6%/−15.4%；真正的大头是**四张表全算**的 −27.8%/−36.1% |
| "那就**删掉**那次 `copy`（一行实验）" | ❌ **删不得**：那次复制是元素把自己的显式参数（`class`/`style`/`on_click`）写进去的**私有草稿纸** —— 删了会**污染调用方的 `Attrs`**（同一个 Attrs 传给第二个元素就继承第一个的属性，真 bug）。**正解是让复制变便宜，不是取消它** |

**另一件事更值钱，而且它根本不是"优化"而是"功能没接上"**：上游 0.16 的 `@html.memo` 在我们这条
React 通道上**原来是空转的**（翻译层把 `VNode::Thunk` 的哈希丢了）。本轮接上之后，同一个负载
**每帧新建元素 7007 → 7**，`dom` 档 **14.29 → 0.43 ms（−97%）**（§11）。
⚠️ 那是"只有表头在变"这个访问模式的上界，**别把这个数搬到真实应用上**。

与 `PLAN.md` §4.2 排第一的嫌疑点（标签表）的关系不变：那条**成立但只值 ~10%**（D3 实测，§4）。

## 3. 基线（translate 档 = 只算翻译层，**不含 React**）

负载形状见 [`perf-bench/README.md`](../examples/apps/perf-bench/README.md)：每行 4 个作者元素 + 3 个自动
`Text` 包装 = 树上的 7 个元素、1 个 handler、4 个 style 对象（实测元素数与理论值 `7N+7` 每次都对得上）。

### 3.1 两个批次的测量条件**不同**（先读这条，否则数字会打架）

| 批次 | 时间 | 机器状态 | 结论 |
|---|---|---|---|
| **首测** | 10-02 上午 | ⚠️ **同一仓库里有另一份工作在跑**（实测到 `npm/moobile-host/lib/init.js`、`lib/migrate/scan.js` 在本轮内被改，不是本轮改的） | 只有**相对**差值可信，绝对值偏悲观 |
| **重测** | 10-02 晚（22:47 之后） | 那一份工作**已停手 4 小时**（最后一次写文件 18:30） | **本节的权威数字** |

⚠️ 两次之间宿主副本还从 9 份变成了 13 份（对方新增 4 个 `zhouyi-reader*` 应用并跑了
`refresh_host_copies.sh`）⇒ **跨批次比较是被污染的比较**。本文件只做**批次内**的 A/B。

### 3.2 重测（权威）：`min` 统计量、每格 9 次

| N | 元素 | `min` 统计量 | `min` 中位 | 中位的中位 | 每元素 |
|---|---|---|---|---|---|
| 1000 | 7007 | **12.64 ms** | 13.12 ms | 18.9 ms | 1.80 µs |
| 5000 | 35007 | **84.90 ms** | 89.35 ms | 106.8 ms | 2.43 µs |

（"改前"= D3 之前。改后的数字在 §4。）

### 3.3 首测（保留对照，**已被 §3.2 取代**）

| N | `min` 统计量 | `min` 中位 | 备注 |
|---|---|---|---|
| 1000 | 12.51 ms | 14.40 ms | 与重测的 12.64 ms 基本一致 |
| 5000 | 78.94 ms | 89.20 ms | `min` 统计量比重测的 84.90 ms **更乐观** |

⇒ 值得注意：**并发负载并没有让所有数字一致地变差**（N=1000 几乎没变、N=5000 反而更好）。
所以"首测偏悲观"这句话**不能当成一个可以拿来换算的系数** —— 只能得出"两批不可混用"。
N=100（707 元素）只跑过单次：`min` 1.1 ms —— **不构成统计**，只用来标定小规模处的量级。

**为什么报 `min` 而不是中位**：同一份产物连跑，中位数能差 **1.4–1.5×**（§5），
而 `min` 是"最不受 GC 与别的进程干扰的那一次"，是本机条件下最接近"这段代码本身要多少时间"的统计量。
**单次中位数不足以支持任何优化结论** —— 首测的第一版就是这么被误导的。

**这组数字的边界**（读之前先读这里，仪器文件头也写了一样的五条）：

1. **不含 React**：这是翻译层（`VNode → React 元素`）。dom 档才是整条 Web 帧（§6）。
2. **不含布局与绘制**：node 里没有布局引擎，jsdom 也不做布局。真机掉帧里很大一块在这里。
3. **调度是同步的**：量的是"算完这一帧要多少计算"，不是"调度器何时轮到它" ⇒ 这组数字**天然是下界**。
4. **V8 而非 Hermes/JSC**：常量会差，**曲线的形状**（≈线性、每元素 ~1.7–2.4 µs）才可迁移。
5. **负载是**非虚拟化**的**：1000 行一次性全渲染。真实应用用 `FlatList` 一类**虚拟化**时，
   每帧元素数是"可见行数"（十几行），不是 N —— 所以**别把 84.9 ms 读成"真机会掉帧"**。
   可迁移的是**每元素常数**与"成本随元素数线性增长"这条形状。

## 4. D3（标签表索引化）：重判 **−10.5%**（N=5000）/ **−7.6%**（N=1000）

`PLAN.md` §4.2 的嫌疑点 #1 说"`map_tag` 每次调用都新建 44 条数组 + 线性扫描"，预期是主要成本。
**实测：成立，但只值 ~10%。**

| N | 改前 `min` 统计量 | 改后 `min` 统计量 | 变化 | 9 次 `min` 的区间 | 区间重叠？ |
|---|---|---|---|---|---|
| 1000 | 12.64 ms | 11.68 ms | **−7.6%** | [12.6, 14.6] vs [11.7, 13.1] | ⚠️ 轻微重叠 |
| 5000 | 84.90 ms | 76.00 ms | **−10.5%** | [84.9, 93.7] vs [76.0, 82.7] | ✅ 完全不重叠 |

- **N=5000 上是硬结论**（两个变体各 9 次的 `min` 区间完全不重叠）。
- **N=1000 上只能算"方向一致、幅度更小"**：−7.6%，区间有轻微重叠。
- ⚠️ **首测报的 −10.7%@N=1000 是被并发负载吹大的**：重测降到 −7.6%。
  机制上说得通 —— 改前版本分配更多，在 CPU 争抢下被罚得更狠。**"在负载下量的 A/B 会放大差值"**
  这条本身就是本轮的方法论产出（§5.3）。

改法（`render.mbt`）：加一个**模块初始化时建一次**的 `Map[String, String]` 索引，`map_tag` 查它。
**表本身没有搬家** —— `tools/mbtools/src/migrate_scan.mbt` 是**按文本行**读那张字面量表的
（认 `("tag", …)` 形状），挪成别的形状会让 F1 报告数出 0 条。所以只加索引，不动真源。
**验证**：F1 报告仍是 **44 映射 / 12 排除**（`bash tools/mb.sh migrate-scan --root ../yi/zhouyi_reader`）。

## 5. **灵敏度与噪声**（这份报告最重要的方法论部分）

### 5.1 同一份产物的 9 次读数（重测，ms）

| 变体 | N=1000 的 9 次 `min` | N=5000 的 9 次 `min` |
|---|---|---|
| 改前 | 12.6 12.9 13.0 13.1 13.1 13.2 13.2 13.8 14.6 | 84.9 85.7 86.9 87.8 89.4 92.2 93.4 93.6 93.7 |
| 改后 | 11.7 11.9 12.2 12.3 12.5 12.6 12.7 13.1 13.1 | 76.0 77.8 80.4 80.4 80.5 81.7 82.1 82.5 82.7 |

⇒ **`min` 那一列很紧**（1.12–1.16× 的极差），而**中位数依然散**（改前 N=1000：`min` 中位 13.12 但
中位的中位 18.9 ms，**1.44×**）。所以：

### 5.2 三条结论

1. **单次读数不能用来做 A/B**：同一份产物、同样的代码，中位数能差 1.4–2.2×（首测在并发负载下达 2.2×），
   而 D3 的真实效果是 7–10% —— **用单次中位数会把噪声当成果，也会把成果当噪声。**
2. **`min` 统计量有资格当判据**：9 次里极差只有 1.12–1.16×，且两个 N 上方向一致。
   这就是本轮的"证伪"：**连 7% 都要能稳定测出来，否则这份基线只是噪声的装饰。**
3. **校准哨兵**（同一段固定计算量）重测落在 **15.1–20.5 ms**（探针批次 15.7–20.8 ms）。⚠️ 它自己就有 1.36× 的漂移 ⇒
   仪器报的"条件不稳"警告**不是装饰**：本机即使在"空闲"时也有 ±35% 的瞬时干扰。

### 5.3 本轮新学到的两条（都影响判据口径）

- **同一份产物、跨会话能差 7%**：`art-d3a.js` 在重测批次里是 11.68 ms，在探针批次里是 12.49 ms
  （同一个哈希、同一台机器、同一组参数）。⇒ **A/B 必须在同一个会话里交错跑**，
  跨会话只能比"区间是否重叠"，不能比绝对值。
- **在负载下量的差值会被放大**：§4 那条（−10.7% → −7.6%）。
  ⇒ 想要可比的差值，**先确认机器上没人在跑别的活**。仪器会打哨兵正是为了这个。

## 6. `dom` 档（真 React + jsdom）—— **本轮补上统计口径**（2026-10-03）

> ⚠️ 此前这一档**只做过冒烟**（旧版这里写着"明确留到下一轮"）。本轮把它做成能当判据的东西，
> 代价是先发现**它的量纲取决于 `NODE_ENV`** —— 这正是"没记录的测量条件等于不可比的读数"。

### 6.1 量纲取决于 `NODE_ENV`（先读这条，否则数字会打架）

| 条件 | 事实（都是实测） |
|---|---|
| `NODE_ENV=production`（本机 shell 默认） | `require("react")` 走 `react.production.js`，而**它不导出 `act`**（`act` 只在 development 构建里；`react-dom/test-utils` 那个只是转发，production 下同样不可用） |
| 没有 `act` 时"一帧"是什么 | **`dispatchEvent` + 一个微任务**。实测：`dispatchEvent` 返回时 DOM **还是旧的**，推进发生在一个微任务之后 |
| 那层微任务的地板 | **0.001–0.002 ms**（量出来就是为了说明"没有地板要扣"）；`act_floor_ms` 在 production 档报 `null` |
| `root.render` 的坑 | React 19 的 `root.render` 是**并发**的：不冲刷的话"挂载完"其实还没落地（`act` 那条路把它挡住了，production 档一跑就暴露）。用 `flushSync` 挂载 |

⇒ 仪器把 **`NODE_ENV` / React 构建类型 / 冲刷方式**写进读数（`env.node_env` / `env.react_build` / `env.dom_flush`）。
**比读数之前先对这三项**：同一个仓库、同一份产物，两个 shell 的 `NODE_ENV` 不同就是两种量纲。

### 6.2 每帧**自证落地**（第四条自证机制）

`dom` 档每帧**比对表头的 `tick` 有没有推进**，并报 `frames_landed / missed / dropped`：

- `missed` = 那一帧要靠**计时区外**的一个宏任务补一次（计时有偏，但要记账）；
- `dropped > 0` = **这一帧根本没落地，这一次的读数作废**（不是"很快"）。

这条不是装饰 —— **它第一次跑就抓到了下面 6.4 那个 bug**（当时报出来每帧 0.03 ms，而帧压根没发生）。

### 6.3 数字（N=1000，`min` 统计量，同会话交错 9 轮）

| 档 | 产物 | `min` 统计量 | 9 轮区间 | 元素数 |
|---|---|---|---|---|
| `translate`（只翻译层） | `bc793b30f6487957` | **8.704 ms** | [7.764, 11.120] | 7007 ✓ |
| **`dom`（真 React + jsdom）** | 同上 | **14.288 ms** | [13.052, 16.454] | 7007 ✓ |
| ⇒ **React 的 diff/commit + DOM 调用那一份** | | **≈ 5.6 ms（39%）** | | 每元素 ~0.80 µs |

- 两档**同一份产物**、同一会话、交错跑（这条是 `PERF.md` §5.3 的老规矩）。
- ⚠️ **边界照旧**：jsdom **不做布局**、它的 DOM 比真浏览器慢 ⇒ 绝对值偏悲观、只有差值方向可信。
- 归因见 §6.4：React 内部（`beginWork` / `commitMutationEffectsOnFiber` / `commitHostUpdate` / `updateSlot`）
  与 **jsdom 的样式机器**（`CSSStyleDeclaration` / `get style` / `setProp` / `updateProperties`）各占可观一份，
  **后者不可迁移**（真浏览器里没有这段）。

### 6.4 这一档逼出来的两个仪器 bug（都会**静默**给错读数）

| 现象 | 真因 | 修法 |
|---|---|---|
| 每帧 **0.03 ms**、`act` 报 "is not a function" | **`NODE_ENV=production`** ⇒ 没有 `act` | 两条计时路（§6.1） |
| 帧"跑完"但 **DOM 一直没动**（`React error #31`：`object with keys {type,key,props}`） | dom 档数元素时换的**桩 React** 返回的是仿制品 `{type,key,props}`，而运行时**缓存着那棵树** ⇒ 换回真 React 时渲染到的是**桩元素的树** | 改成**计数代理**（`makeCountingReact`）：记完账照样调用**真** `React.createElement` |
| `--profile` 报 **98.4% `spawnSync`**（像"采样坏了"） | 中间进程因缺 `--expose-gc` **又 re-exec 了一次** ⇒ 目录里两份都"新鲜"的 profile，代码按目录顺序挑，**挑中了只负责拉起子进程那一层** | 子进程给足 `--expose-gc`（不再 re-exec）+ 有多份时**挑采样最多的**；并把 `>50% spawnSync` 做成**会自己喊出来的签名** |

### 7.1 先说**读代码读出来的那张图**（首测，`--profile`，V8 CPU 采样）

### 7.2 ⚠️ 那张图**指向的地方，读代码时被读错了**（本轮更正）

上一版写的是：

> "1. `Attrs::styles(s)` 把扁平数组逐条塞进**不可变 HAMT** …
>  2. `render_props` 调 `props.styles_map()`，而它（`vdom.mbt:163`）是 `copy_map(self.styles)`"

**逐条核实的结果（三个事实，都直接读源码得到的）**：

| 上一版的说法 | 实际代码 | 证据 |
|---|---|---|
| `Map` 是**不可变 HAMT** | ❌ **可变** LinkedHashMap（`mut entries : FixedArray[…]` + grow/rehash） | `~/.moon/lib/core/builtin/linked_hash_map.mbt:42` |
| `styles_map()`（`:163`）是 `copy_map(self.styles)` | ❌ `styles_map()` 在 **`:221`**，实现就是 `self.styles` —— **只读、零复制** | `vendor/rabbita/vdom/vdom.mbt:221-223` |
| （隐含）复制只发生在 styles 上 | ❌ `copy_map` 在 **`:163`，属于 `Props::copy`**，对**四张表**各一次 | `vendor/rabbita/vdom/vdom.mbt:158-165` |

**真正的热路径**（每元素每帧）：

```
html.mbt:40   resolve_attrs(Some(a), …) → a.copy()      ← 每个元素都走
attrs.mbt:28  Attrs::copy = Attrs(self.0.copy())
vdom.mbt:158  Props::copy → copy_map × 4（handlers / attrs / props / styles）
```

> ℹ️ **这些行号取自 P1 之前的树**。P1 落地后 `vdom.mbt` 里已经没有 `copy_map` 了
> （`Props::copy` 现在是 O(1) 指针拷贝），行号也全变了 —— **这正是"别把行号当结论"的现场示范**
> （§10-6）：引用代码事实请以**函数名**为准。

**这个更正有实际后果**：那条"一行实验"（去掉 `styles_map()` 的 `copy_map`）**会改在空处** ——
那里本来就没有 `copy_map`。而且 `Map` 既然是**可变**的，`copy_map` **不是白花的**：
去掉它会让"副本"与"原件"共享同一张表，改副本会漏回原件（`Attrs::copy` 的注释
"Return an independent copy that can be extended without mutating `self`" 说的就是这件事）。
⇒ **"去掉那次复制"不是一行实验，而是一次语义决策**（见 §8）。

### 7.3 ★ 实测：消融探针把这一刀量出来了（本轮的核心产出）

**方法**：把 `Props::copy` 改成**共享**而不是复制（`vendor/rabbita/vdom/vdom.mbt`，**临时改动、测完字节级还原**），
构建成留档产物，再与"当前树"（D3）**在同一会话里交错跑**。两个消融：

- **探针 B（`nocopystyle`）**：只共享 `styles`，其余三张照旧复制；
- **探针 A（`nocopy4`）**：四张全共享。A 与 B 的差 = 另外三张表的代价。

**为什么在本负载上这个消融是干净的**：`perf-bench` 的每个元素都是**全新的** `Attrs::build()`
（`app.mbt` 的 `attrs()` 辅助函数），没有任何人复用同一个 `Attrs` ⇒ 别名污染不会发生。
仪器实测三组变体的负载形状**逐项相同**（7007/35007 元素、4005/20005 样式、1001/5001 handler、`shape_ok` 全 true）
⇒ 这是**纯成本移除**，不是"换了负载"。

**读数（各 9 次，同一会话交错，`min` 统计量）**：

| 变体 | N=1000 | vs 对照 | N=5000 | vs 对照 |
|---|---|---|---|---|
| 对照（当前树 = D3） | 12.49 ms | — | 79.92 ms | — |
| **只共享 `styles`**（B） | 10.56 ms | **−15.4%** | 75.41 ms | −5.6% |
| **四张表全共享**（A） | **7.99 ms** | **−36.1%** | **57.67 ms** | **−27.8%** |

**折算成每元素**（消除复制省下的时间 ÷ 元素数）：

| 消融 | N=1000 | N=5000 | 一致吗 |
|---|---|---|---|
| 四张全共享（A） | **0.643 µs/元素** | **0.635 µs/元素** | ✅ 几乎完全相同 |
| 只共享 styles（B） | 0.275 µs/元素 | 0.129 µs/元素 | ❌ 差 2 倍 |

⇒ **四条结论**：

1. **"每帧重建 Map 约占四成"这条归因成立**，而且**主要不是 styles 那一份**：
   四张表的复制**自己就占 28–36%**。上一版把账记在 styles 的"第二次重建"上，**方向对、比例错**。
2. **每元素常数在两个规模上一致（0.643 / 0.635 µs）** ⇒ 这是真的每元素成本，不是规模效应或噪声。
3. **探针 B 的每元素数字在两个规模上差 2 倍** ⇒ 那一份的估计**不可靠**（可能是 N=5000 上
   与 GC 重叠所致），所以"styles 那一份值多少"这句话本轮**只敢说 −5.6%~−15.4%**。
4. **机制（推测，未单独验证）**：`copy_map` 对每张表都做一次 `Map([])` —— 那是一次
   **backing array 分配**，**哪怕源表是空的也要分配**。而本负载里 `attrs` / `props` 表对绝大多数元素
   都是空的、`handlers` 只有 1001/7007 个元素非空 ⇒ **28k 次/帧的 Map 分配里有一大半是空表的**。
   这正好对上 §7.1 里"`make_array_len_and_init` 14.1%，其 95% 父函数是 `new_map`"与 GC 19.9%。

> ⚠️ **探针 A 是"上界"，不是"可落地的修法"**：它靠**共享**四张表来量成本，而共享会破坏
> `Attrs::copy` 的独立性契约（可变 Map ⇒ 改副本会漏回原件）。它回答的是"**这些复制一共值多少**"，
> 不回答"**怎么在不破契约的前提下把它去掉**"。

### 7.4 兑现：不破契约地拿到这一笔（P1，**已落地**）

**做法**：把四张表换成**不可变**结构（core 的 `immut/hashmap`），外面包一层 `PropsTable[V]`。
于是 `Props::copy()` 从"逐条重插四张表"变成 **O(1) 指针拷贝、零分配**，
而"每个元素拿到独立副本"这条语义**一点没变** —— 不可变结构的共享天然安全；
"改副本"等于用一张新表替换掉那一格，原件不受影响。

| N | 对照（D3）`min` 统计量 | P1 之后 | 变化 | 9 次 `min` 区间 | 每元素 |
|---|---|---|---|---|---|
| 1000 | 11.20 ms | **7.57 ms** | **−32.4%** | [11.20,12.17] vs [7.57,8.67] ✅ 不重叠 | 1.599 → 1.080 µs |
| 5000 | 72.04 ms | **50.96 ms** | **−29.3%** | [72.04,79.59] vs [50.96,56.85] ✅ 不重叠 | 2.058 → 1.456 µs |

- **三种统计量同向**（−32.4/−32.2/−31.7 与 −29.3/−29.8/−22.5）⇒ 不是噪声。
- **形状断言逐项不变**（7007/35007 元素、4005/20005 样式、`shape_ok` true）⇒ 语义没变。
- **全量门 24/24 通过**，含行为类判据（真实应用 chat-app 22 项、脚手架模板、宿主矩阵 32 项）。
- 省下 **0.52 / 0.60 µs per 元素**，与 §7.3 预言的上界 0.64 µs 吻合（差额被"插入变贵"吃掉）。
- ⚠️ **分配量没有一致的改善**：`heap_delta` 中位数在 N=1000 上是 81 → 98 MB、在 N=5000 上是
  233 → 154 MB（**方向相反**）⇒ 这个读数不足以支持任何结论，**别引用它当"更省内存"的证据**。
- ⚠️ **为什么不是"删掉那次复制"**：那次复制是元素构造器写自己参数的**私有草稿纸**
  （见 §0 第三行）—— 删了会污染调用方的 `Attrs`。**这条路是让复制变便宜，而不是取消它。**

## 10. 纪律（写给下一个人）

1. **先测再优化**：§4 与 §7 都是反例 —— 读代码排第一的嫌疑点只值 ~10%；
   而"真正的大头"在读代码时**连位置都找错了**（§7.2），**是消融把它找回来的**。
2. **不带 `--trials` 的读数不能用来下结论**（§5）。
3. **A/B 要比产物哈希**，并用 `--artifact` 量留档的构建，别在测量中途重编。
4. **改 `app.mbt` 的视图 = 改口径**：`7N+7` 那条断言与这份文件都要同步，否则读数不可比。
5. **消融探针的三条硬规矩**（本轮新增，照做才不会把实验污染成事实）：
   ① 改 `vendor/**` 前先做**字节级备份**（`sha256` 记下来），测完还原并**重新校验哈希**；
   ② 探针**不入 patch 系列** —— 别对半成品跑 `vendor_sync.sh --capture`（那会把实验写进真源）；
   ③ 探针产物与对照**在同一会话里交错量**（跨会话同一份产物能差 7%，§5.3）。
6. **别把"读到的行号"当结论**：本轮就是拿 `:163` 这个行号当成了函数名（§7.2）。
   引用代码事实时，**贴出函数名与它的实现**，不要只贴行号。
7. **"让热的东西变便宜"，而不是"删掉它"**：P1 的第一版想直接删掉那次复制，读代码才发现
   它是元素写自己参数的**私有草稿纸** —— 删了会**静默污染调用方**（§0 第三行）。
   **先问"这个动作为什么在"，再问"能不能让它变便宜"。**
8. **改 `vendor/**` 的正确姿势**（P1 走了一遍完整流程）：字节级备份 → 改 → 构建留档产物 →
   `vendor_sync.sh --capture` → `vendor_sync.sh --check`。
   **`--check` 过了才算这次改动"能被重建"** —— 第三方目录是 gitignore 的，
   `git status` **不会**提醒你漏了 patch。
9. **优先选"编译器强制"的改法**：P1 有两条路 —— 手工给 ~210 个写入点加"共享检查"（漏一处是
   **静默 bug**），或换类型让**编译器**枚举所有需要改的地方（漏一处**编译不过**）。
   选了后者：最终只动了 7 个文件，而上游那 ~200 处写入**一处未动**。
10. **测量条件要写进读数**（dom 档那一课的成品）：`NODE_ENV` 决定 React 是 development 还是 production 构建、
    也决定"一帧"怎么算 —— **没记进读数的条件，等于两份不可比的数字**（§6.1）。
11. **"漂亮得可疑"的数字要先证明那一帧真的发生了**：dom 档那次每帧 0.03 ms，
    真因是**桩元素把真 React 的树毒死了**、帧压根没落地（§6.4）。
    ⇒ 任何"计时循环"都该有一条**逐帧自证**的断言。
12. **机制不明的差值，宁可标注"未解释"，也不要归因给它看起来最像的那个原因**（§11.5）：
    旧库开 memo 快 27~30% 而调用计数相同 —— 如果顺手写成"memo 生效了"，
    整节的结论就错了。**先分清"这是什么"再算"这值多少"。**
13. **消融开关要能让"接线本身"被验证**：`--memo` 是宿主注入的布尔值，
    于是"开/关"两格的**产物哈希完全相同**（§11.6）——
    任何差异都不可能是编译差异，而**没生效时会立刻表现为"形状不符"**。
    （写代码读出来的"这条路径存在"不算接线证据；§11.2 的三层证据里，**实跑那层**才算。）
14. **账本上的收益必须换成墙钟才算数**（§11.6 的教训）：惰性根把 GC 时间砍掉 71%、活对象砍掉 29% ——
    **都是真的、都是直接测量** —— 但三种条件下的 `min`/中位**一动不动**。
    ⇒ 中间量（GC 时间、分配量、元素数）只能用来**解释**结果，不能用来**宣布**结果。
    ⚠️ 附带一条：`min` 对 GC 类改动**天然不敏感**（它取的是最不受 GC 干扰的那一帧），
    量这类改动要另看 `p95` / 均值 / 堆增量。

15. **要给一刀定大小，用消融探针；别用 profile 的份额**（§12.3）：
    profile 的 self time 会被内联与归属漂移吃掉 —— 同一处代码在不同轮次能报 3.2% 与「根本没出现」，
    而消融探针（纯加成本、输出逐项不变）给的是 30%。profile 只适合回答「某个函数还在不在」。
19. **把「只有少数人用得上」的成本从所有人的路上移走时，用「真走一遍 + 这一帧作废」，别用「猜」**（§14.9）：
    按上一次的形状猜这一次有没有 `memo`，省下的记账会以**静默失去功能**为代价；
    而「遇到就是遇到」的重画只有一次成本，且语义与从前逐字一致。
18. **「分配密集」的路径用含时归因，别用加成本探针**（§14.4 → §14.5）：
    加成本探针（多做一遍）会改变 GC 落在哪一帧 ⇒ 均值/p95 能反向（探针「更快」）；
    而**含时归因不新增分配**，因此不扰动 GC。**两次都把结论写进文档，包括反向的那几列。**
17. **回退是一次要验收的改动**（§14.3）：改回去之后要**逐字节比对留档产物**。
    本轮回退 `ArrayView` 时顺手丢了一条快路径（+5.5%），而它是靠 A/B 才发现的 ——
    **区间重叠的 +5% 也值得追**：真因比噪声更常见。
16. **`moon check` 查不到行为，门里必须有 `moon test`**（§12.1）：P1 把上游的
    `attrs_copy_test.mbt` 弄红了却没人知道，因为那次改动只跑了 `moon check` + 离线门。
    **「类型过 + 端到端过」不等于「语义过」** —— 白盒测试补的正是中间那一格。

## 11. memo：把 0.16 那把刀**接上**（2026-10-03）

### 11.1 结论

上游 0.16 给了 `@html.memo` / `memo_by`（产物是 `VNode::Thunk(hash, f)`）。**我们这条 React 通道上它原来是空转的** ——
`render.mbt` 的匹配臂是 `Thunk(_, f) => render_node(f(), sched)`：**哈希被直接丢掉、永远强制求值**。
本轮把它接上（§11.3），实测（N=1000，同会话交错 9 轮，`min` 统计量）：

| 档 | memo 关 | memo 开 | 变化 | 9 轮区间 | 每帧新建元素 |
|---|---|---|---|---|---|
| `translate` | 8.704 ms | **0.133 ms** | **−98.5%** | 不重叠 ✅ | 7007 → **7** |

> ⚠️ **这两个百分比是在 P1b 之前的树上量的**；P1b 之后重测为 **−97.5% / −96.9%**（§13.4）——
> 结论不变、幅度略小。**引用请用 §13.4 的数字。**
| `dom` | 14.288 ms | **0.430 ms** | **−97.0%** | 不重叠 ✅ | 7007 → **7** |

每帧 handler **1001 → 1**、style 对象 **4005 → 5**。

> ⚠️ **这是"只有表头在变"这个访问模式下的上界**：本负载每帧只改表头那一个数字，所以**整片行都命中**。
> 真实应用改得更多、命中更少 ⇒ **可迁移的是机制，不是这个 −97%**。

### 11.2 "空转"是**三层证据**，不是读代码的推断

| 层 | 证据 |
|---|---|
| 源码 | `render.mbt` 的 `@vdom.VNode::Thunk(_, f) => render_node(f(), sched)`（哈希丢在 `_` 里） |
| 编译产物 | `art-memoknob.js` 里那段：`const _Thunk = v$2; const _f = _Thunk._1;` —— **`_Thunk._0`（哈希）从未被引用** |
| 实跑（计数） | 临时给负载加计数器（测完按字节还原）后的**每帧调用计数**： |

| 库 | memo | `view` /帧 | `row_html` /帧 | 元素 /帧 |
|---|---|---|---|---|
| 旧（无 memo 支持） | 关 | 1.00 | 1000.00 | 7007 |
| 旧 | 开 | 1.00 | **1000.00** | **7007** |
| 新（本轮） | 关 | 1.00 | 1000.00 | 7007 |
| 新 | 开 | 1.00 | **0.00** | **7** |

⇒ 旧库开不开 memo **一模一样**（连 `view`/`row_html`/元素三类调用计数都逐项相同）；新库开 memo 时 `row_html` **一次都没被调用**。
**开 memo 与不开 memo 的 `row_html` 调用次数（1000 vs 0）就是"接上了没有"的判据。**

### 11.3 接法：`MCtx` —— 按**孩子序号路径**定位的惰性缓存

新增 `MCtx` / `MCache`（`render.mbt`），每个**挂载点**一份（放在 `Frame` 里，不是模块全局）。
`Thunk` 位置记住上一次的 `(哈希, 元素)`，哈希不变就**原样返回那个元素对象** —— React 拿到同一个元素引用，自己跳过整棵子树。

三条设计决定（每条都有理由，都是被"不能给大多数人加税"逼出来的）：

1. **按路径定位、不按遍历序号**：路径（`[1, 5]` = 根的第 1 个孩子的第 5 个孩子）才是"同一个位置"。
   扁平表会在结构变动时把**不相干的两个 thunk** 对到一起 —— 那类错配会**静默画出旧内容**；
   路径定位下最坏只是"键不同 ⇒ 重算"，**不会画错**。
2. **惰性**：缓存节点只在**真的遇到 `Thunk`** 时建。不用 memo 的应用**零分配、零哈希表操作**（§11.4 是它的代价）。
3. **未命中时原地往下画**：内层 memo 走到更深一层的路径上 ⇒**嵌套 memo 也能命中**。

### 11.4 代价与边界（都实测过）

| 项 | 结果 |
|---|---|
| **不用 memo 的应用要付什么** | `translate` **+2.0%**（9 轮区间**重叠** ⇒ 在噪声内）、`dom` **+0.4%**。机制上确实多了每节点一次"路径记账"（`enter`/`leave`）⇒ **进了下一轮清单**（见 §8） |
| **语义** | 单测探针实测（memo 开）：点某一行 ⇒ **那一行的 DOM 真的变**（`rgb(255,250,240)` → `rgb(255,233,201)`）、**邻行不动**、再点一次**回到初始**。缓存不会给出旧内容 |
| **键给错的后果** | 画旧内容 —— 这是 **memo 自己的契约**（"键相同必须蕴含 HTML 与 handler 等价"，上游 `html.mbt` 原话），不是我们加的。位置键（`by = 行号`）在列表头部插入一行之后就会错配 |
| **内存** | 缓存按结构位置存活到挂载点消失（列表缩短时旧格子还在，但不引用别的活对象）。`heap_retained` 实测仍是 ~0.2 MB |

### 11.5 ✅ 那条"未解释"的实测**查清了**：不是记忆化，是"这棵树在不在 GC 眼里"

`gc_probe`（`.scratch/perf/gc_probe.mjs`：每帧 gc 后量**活对象** + `PerformanceObserver` 记 GC）+ 四格对照：

| 格 | **每帧 gc 后活对象** | GC 总时间 / 100 帧 | 单次 Scavenge | 每帧分配 |
|---|---|---|---|---|
| 旧库 · memo 关 | **11.73 MB** | 202.3 ms（30 次） | 6.5 ms | 17.7 MB |
| 旧库 · memo 开 | **8.74 MB** | 56.7 ms（29 次） | 2.0 ms | 18.2 MB |
| 新库 · memo 关 | 11.90 MB | 216.5 ms（30 次） | 6.8 ms | 18.0 MB |
| 新库 · memo 开 | 9.02 MB | 1.0 ms（4 次） | 0.25 ms | 0.31 MB |

**机制（现在是量出来的，不是猜的）**：`model_node.map(m => view(m, emit).to_virtual_dom())` 让 duplix 节点
把**整棵 VNode 树当作"当前值"持有到下一帧**（差的 ~3 MB 正好是 N=1000 一棵树）。
那份数据在新生代 GC 触发时是**活的** ⇒ 每次 Scavenge 都要**复制**它 ⇒
**同一种 GC、同样的分配量，单次代价 2.0 → 6.5 ms**。

⚠️ **"晋升到老生代"那个假设被证伪了**：四格都**没有** Mark-Compact（全是 Scavenge）。
差别不在"哪一种 GC"，而在"**同一种 GC 一次要搬多少活对象**"。

⚠️ **效应大小取决于机器状态**（§5.3 的又一例）：早先那批的哨兵是 **16.2 ms**、今天这批是 **12.2 ms**
（机器快 ~25%）——**同一份产物** `bc793b30f6487957` 在 `min` 上从 **8.70 ms** 变成 **5.90 ms**。
而"去掉保留量"这类改动在**慢/抢 CPU**的条件下差值被放大：早先那批 `min` 上表现为 −27~30%，
今天安静机器上只体现在**尾部**（见 §11.6）。⇒ **跨批次比绝对值的坑，这一轮又踩了一次。**

### 11.6 顺着这条机制做的实验：**根视图惰性化**（结论：**回退了** —— 墙钟换不来）

既然"活对象"来自 duplix 持有那棵树，就试了把它换掉（`app.mbt`）：

```moonbit
let mut gen = 0
model_node.map(m => {
  gen = gen + 1
  @vdom.VNode::thunk(gen, () => view(m, emit).to_virtual_dom())
})
```

（模型每变一次换一个新哈希 ⇒ **一定**重画；顺带白拿"模型没变 ⇒ 翻译层直接命中缓存"。）

**直接测量（机制层面，全部成立）**：

| 判据 | 对照 | 惰性根 |
|---|---|---|
| 每帧 gc 后**活对象** | 11.90 MB | **8.43 MB** |
| GC 总时间 / 100 帧 | 216.5 ms（30 次 Scavenge） | **63.6 ms**（28 次） |
| 净堆增量（translate） | 97.5 MB | 30.7 MB |

**墙钟（三种条件下各跑一次交错 A/B）**：

| 条件 | `translate` `min` | `translate` 中位 | `translate` p95 | `dom` `min`/中位/p95 |
|---|---|---|---|---|
| 安静机器（9 轮） | −1.5%（重叠） | +0.2%（重叠） | **−19.4%**（重叠） | 全部重叠 |
| 12 忙进程抢 CPU（6 轮） | −2.0%（重叠） | −2.4%（重叠） | **−15.1%（区间不重叠 ✅）** | 全部重叠 |
| **V8 线程池=1 + 半空间 2 MB**（6 轮，手机代理） | **+0.5%**（重叠） | **+1.9%**（重叠） | — | **+2.9% / +2.3%**（重叠） |

⇒ **典型那一帧（`min`/中位）在三种条件下都不动**，`dom` 档一次都没动过，
第三档（GC 压力最大的那个条件）甚至略差。**按本仓库的门槛（区间不重叠）不成立 ⇒ 已回退。**
（回退后重建的产物与 A/B 用的对照产物 `bc793b30f6487957` **字节相同** ⇒ §11 的 memo 读数不受影响。）

⚠️ **我先前写在这里的解释是错的，按规矩留档更正**：曾写"V8 的 Scavenge 会用到后台线程 ⇒ 16 核空闲时被吸收"。
**不对**。第三档（线程池=1 **且** 半空间 2 MB）里 GC 账本**根本不差**：**662.8 ms vs 687.2 ms**（1016 vs 1043 次 Scavenge）。
真因是**那棵树会不会被 Scavenge 复制**：

- 半空间**大** ⇒ 3 MB 的树待在新生代里，每次 Scavenge 都要**复制**它（216 → 63 ms，差别全在这）；
- 半空间**小** ⇒ 它很快**晋升**到老生代，Scavenge 根本不碰它 ⇒ 两个变体没区别（662 ≈ 687 ms）。

⇒ **"保留量"这一项的代价取决于年轻代有多大，而不是核多核少。**

⚠️ **对目标平台的推断（是推断，未验证）**：Hermes 的 GenGC 年轻代本来就只有几 MB
⇒ 按上面那条机制，惰性根在真机上**大概率也换不来墙钟**。要判就得真机（D2 的 `dumpsys gfxinfo`）。

**保留下来的东西**：这条机制本身（它是"view 的产物会被图持有"这个事实的**直接测量**，
对任何"每帧重建大树"的框架都成立）、两个留档产物（`art-lazyroot.js` / `art-memo-fix.js`）、
以及下面这条方法论。

⚠️ **这一轮暴露了 `min` 统计量的一个盲区**（方法论，已补进 §10 第 14 条）：
`min` 是"**最不受 GC 干扰的那一帧**"，所以它对 **GC 类改动天然不敏感**。
§3 选它的理由（抗并发负载与噪声）依然成立，但**量 GC/内存类改动必须另看 `p95` / 均值 / 堆增量** ——
而这一次连它们也没能站住（三种条件里只有两档 p95 的方向一致）。

### 11.7 这一轮为它加的仪器能力（都能复用）

- `--memo`：宿主在 `app()` 之前注入 `globalThis.__MOBILE_BENCH_MEMO__`（负载 `perf-bench/app.mbt` 里的消融开关）
  ⇒ **同一份产物**跑两格，A/B 不必重新编译（这才是"比产物哈希"最干净的形式）。
- **memo 专属的形状预期**：`--memo` 档预期每帧 `7` 个元素（不是 `7N+7`）。
  ⚠️ 这不是放宽断言 —— **memo 没生效时实测会是 `7N+7`，`shape_ok` 照样红**，而且会多打一句"★ 这是 memo 没生效，不是负载变了"。

## 12. P1 的一个**已发出的正确性回归**（本轮修掉）+ 插入成本到底值多少（2026-10-03）

### 12.1 回归：`Props::copy` **不独立**（上游自带的白盒测试抓到的）

跑一次 `moon test`（**门里原来没有这一格**）就红了：

```
test "Attrs::copy isolates later mutations" — FAILED
-None            （期望：原 Attrs 上不该有 aria-label）
+Some("Copied")  （实际：往副本里写，**漏回了原件**）
```

**真因**：`PropsTable` 是**可变对象**（`set` 原地改写 `entries` 那一格），而 P1 的第一版
`Props::copy()` 把那四张表**连句柄一起共享** ⇒ 副本与原件**是同一批表对象**，写副本等于写原件。
这**正是 `PERF.md` §0 警告过的那类静默污染**（同一个 `Attrs` 传给第二个元素，第二个元素就把属性写进了第一个）。

**为什么一直没被发现**：① `moon check` 只查类型、查不到行为；
② **`tools/verify_all.sh` 里没有 `moon test`**（本轮补上了，见 §12.4）；
③ 基准负载里每个元素都拿**全新的** `Attrs::build()`，所以它的形状断言看不见串味。

**修法**：新增 `PropsTable::share()` —— 只共享**不可变数据**（HAMT 根），
**句柄各自新建**。复制仍是 O(1)、不逐条重插（P1 的收益在），而"副本与原件互不可见"这条语义变成真的。

**修它的代价（实测）**：把"共享句柄"改成"新建 4 个句柄"（每元素每帧 4 次小分配）

| 档 | min | 中位 | 均值 | p95 |
|---|---|---|---|---|
| `translate` | +12.2%（区间重叠） | **+6.3%** | **+7.6%** | +1.2% |
| `dom` | +4.3% | +2.7% | +1.5% | +1.1% |

⇒ **P1 的净收益从 −32%（N=1000）降到约 −25%**。**这是正确性的价格，不是可选项。**

### 12.2 顺带做掉的（P3a）：`PropsTable::is_empty()` 原来是 **O(N)**

core 的 `immut/hashmap` 把 `HashMap::length()` 明确标成 O(N)（`WARNING: this operation is O(N) in map size`），
而 `is_empty()` 就是 `length() == 0` —— 它**每元素每帧**被问一次（`render_props` 靠它决定要不要写 `style` 键）。
新增一个**保守非空位**（`set` 置真；`remove` 是罕见路径、在那里重算一次）⇒ O(1)，**语义精确**。

⚠️ **墙钟上测不出来**：`translate` 中位 −0.9%、`dom` −0.9%，**区间全部重叠**（在噪声内）。
原因也查清了：`immut/hashmap` 的 `length()` 对**小表**（Flat 节点）直接返回 1、根本不做那个 O(N) 遍历
（`node_size(Flat(_)) => 1`）—— 我们的样式表只有 4 条，所以省下的近乎为零。
**保留它的理由**：它去掉的是一个**有文档背书的 O(N)**（大表/属性多的元素会真的中招），且不改语义。
**不保留的理由**：它没换来可测的墙钟收益，而 vendor patch 面多了一点。

### 12.3 ★ 插入成本到底值多少：**对称消融探针**（本轮最有用的一个数）

profile 说样式插入只占 3.2% —— 但 profile 的**份额**这一轮已经两次不准（§12.2 与 §11.6）。
所以改用**纯加成本**的探针：把 `Attrs::styles` 里"每插一条样式"这件事**做 3 遍**
（同样的键、同样的值 ⇒ **输出逐项不变**：7007 元素 / 1001 handler / 4005 样式，`shape_ok` 仍为 true）。

| N=1000 · translate · 8 轮交错 | min | 中位 | 均值 |
|---|---|---|---|
| 对照（插 1 遍） | 5.90 ms | 7.60 ms | 8.95 ms |
| 探针（插 3 遍） | **9.52 ms** | **10.47 ms** | 11.56 ms |
| ⇒ 差值 | **+61.4%（区间不重叠 ✅）** | +37.8% | +29.1% |

**反推**：多出来的 2 遍 = 8010 次额外插入/帧 ≈ 3.6 ms ⇒ **每帧那 4005 次样式插入约值 1.8 ms
（翻译层的 ~30%）**，而 **profile 说 3.2% —— 低估了一个数量级**。

⚠️ **方法论（补进 §10 第 15 条）**：profile 的 **self time 份额**会被内联/归属漂移吃掉

## 13. P1b：样式表改**扁平数组**（2026-10-03 —— 本轮最大的一刀）

### 13.1 先探针、后动手

`§12.3` 的对称探针（把"每插一条样式"做 3 遍、输出逐项不变）给出 **min +61.4%（区间不重叠）**
⇒ 反推现存那一遍约值 **1.8 ms/帧 ≈ 翻译层的 30%**，而同一处的 profile 份额只报 **3.2%**。
**先有这一刀的大小，才动手改类型。**

### 13.2 改法：`Styles`（扁平数组 + 可变句柄 + 数组永不原地改）

`Props.styles` 从 `PropsTable[@style.StyleValue]`（不可变 HAMT）换成 `Styles`：

| 不变式 | 为什么必须是它 |
|---|---|
| `entries` 指向的数组**永不原地修改**，所有"改"都换成新数组 | 两个句柄共享同一个数组才安全（`props.styles` 是**每元素每帧**都在写的东西） |
| **句柄本身可变**（`mut` 字段 ⇒ `Styles` 是引用类型） | `Props` 是**值类型**，`Props::styles()` 只能"就地"写进那一格；这也是 `PropsTable` 的既有形状 |
| 存进来的数组是从调用方**复制**的 | `@style.Style` 的构造器是**可变**对象：调用方之后继续用它，不能影响已经存下的内容 |
| 合并语义 = **后来的赢**（键去重） | 与原来 HAMT 覆盖的语义逐条一致 |

写入只有三处：`Attrs::styles`（`html/attrs.mbt` 与 `svg/attrs.mbt`）、`Props::styles`。
读取侧：`is_empty` **O(1)**（数组长度）、`get`/`contains` **线性扫**（表只有几条，比哈希快）、
`iter2` 给 `for name, value in styles` 用（`diff.mbt` / `ssr.mbt` / 我们的 `render.mbt` 都靠它）。

### 14.2 试过又退掉：`Styles` 用 `ArrayView`（类型保证只读）—— **更优雅，但更慢**

用"产物哈希是否回到原值"验收它。**区间重叠的 +5% 也值得追**：它这次是真因，而真因比噪声更常见。

### 14.4 P3 的探针：**属性 → JS 对象**这一笔值多少（以及这次探针为什么不干脆）

做法与 §12.3 同款：把 `render_props` 里"属性表 → JS 对象"的构造**整个再做一遍、丢掉结果**
（输出逐项不变：7007 / 1001 / 4005，`shape_ok` ✓ ⇒ 纯成本加一倍）。

| N=1000 · `translate` · 8 轮交错 | min | 中位 | 均值 | p95 | 堆增量 |

| 默认（半空间默认） | **+23.2%** | **+14.1%** | −1.2% | −29.2% | −20.6% |

**读法（重要，别把这张表读成"P3 = 20%"就完事）**：

1. **`min` / 中位**（本仓库一直用的两个统计量，也是**最不受 GC 干扰**的两个）在两次测量里

4. 顺带落一条**下一轮的具体改法**（还没做）：现在 `render_props` 是**每个键一次 FFI**（`js_obj_set`），
   N=1000 时每帧约 3.5 万次跨界；**批量接口**（把键/值数组一次交给 JS 建对象）是这笔的主要可疑点。
   要先做纯探针把它与"属性表遍历本身"分开，再动手。

### 14.5 顺着**含时**归因做的两刀（P3）：空表不建迭代器 + 样式走索引

**换了个量法**：§14.4 的探针会扰动 GC（多造一倍垃圾改变了"GC 落在哪一帧"），
所以这一步改成算**含时（inclusive）**归因 —— 读 `.cpuprofile`，把每个采样加给它**自己和所有祖先**
（工具：`.scratch/perf/cpuprofile_tree.py`）。它**不新增任何分配**，因此不扰动 GC。

`render_props` 含时 **20.5%**（与探针说的 20~25% 吻合），里面三块：

| 块 | 含时 | 里面是什么 |
|---|---|---|
| `render_props` **自身** | **8.1%** | 两张**在本负载里全空**的表各自的**迭代器构造** + 每元素一个 `js_obj_new` |
| `styles_to_js` | **6.9%** | 自 4.6% + **`Iter2::next` 机制 1.3~2.4%**（P1b 里写的是**闭包迭代器**）+ `js_obj_set` |
| `each_handler` | **4.9%** | HAMT 的迭代机制（自 3.7%） |

**做了两刀**（都不改语义）：

1. **空表不建迭代器**：`render_props` 里 attrs / props 两张表 `is_empty()` 为真就**不进循环**
   （`for k, v in 表` 每次都要先构造一个迭代器；而 `is_empty()` 现在是 O(1)，§12.2）。
   本负载里这两张表在 7007 个元素上**全是空的**。
2. **样式走索引遍历**：`styles_to_js` 不再 `for k, v in styles`（闭包迭代器 = 每元素一次间接调用 +
   一个 `Option[(K,V)]`），改用新增的 `Styles::at(i)` 按序号取。

| N=1000 · 10 轮交错 | min | 中位 | 均值 | p95 | 堆增量 |
|---|---|---|---|---|---|
| `translate` | **−20.7%（不重叠 ✅）** | **−16.7% ✅** | **−28.4% ✅** | **−40.8% ✅** | −46%（✅） |
| `dom` | −9.6%（重叠 ⚠️） | −9.4% ⚠️ | −8.6% ⚠️ | −8.2% ⚠️ | +111%（重叠，噪声） |

⇒ **`translate` 四列全部不重叠**；`dom` 上**四列同向**但**区间重叠** ⇒ 按本仓库的门槛
**只能说"方向一致"**，不是硬结论（`dom` 里 React 占近一半，这一刀被摊薄）。

**还剩的一块（没做）**：`each_handler` 那 4.9% 是 HAMT 的迭代机制 —— 它要的是"**小表用扁平结构**"，
也就是把 P1b 对样式做过的事，对 handlers 再做一遍（写入点在 vdom 内部，可控）。
`render_props` 自身那 8.1% 里还有每元素一个 `js_obj_new`。

### 14.7 落到**真应用**上：chat-app 的消息列表（本轮，比继续抠微优化更贴目标）

helper 与配方只是"能用"；**真的用起来**才算落地。选 chat-app 的消息列表，因为它的形状**恰好**是
memo 的主场：**流式**时每来一段只有"最后那条"变，其余每一条都没变。

```moonbit
// examples/apps/chat-app/app.mbt —— 原来是 model.bubbles.mapi((i, b) => bubble_row(b, sending && i == n - 1))
@moobile.memo_list_i(
  model.bubbles,
  by=(i, b) => bubble_key(b, sending && i == n - 1),
  f=(i, b) => bubble_row(b, sending && i == n - 1),
)
```

**键必须是"这一行用到的每一个会变的东西"**，这条在 chat-app 上是三样（少一样就有一个可见的坏症状）：

| 键里装的 | 少了它的症状 |
|---|---|
| `b.role` | 「你」/「AI」的标签与配色**停在旧值** |
| `b.text` | 流式长出来的字**画不出来** |
| `streaming_tail`（`sending && i == n-1`） | 生成中的光标**不出现 / 不消失** |

⇒ 新增了**带序号**的 helper `memo_list_i`（行的渲染常常依赖"第几条"），
并在 `verify.mjs` 里加了一条**端到端判据**（chat-app 无头判据 **22 → 23 项**）：

```
PASS  ★ 流的每一段只重算「正在生成的那条」，其余行命中 memo  <- 这段里 命中 +4 · 未命中 +4
```

**这条断言为什么这么写**（两个数都要涨，缺一个就说明坏了）：

- 只涨**命中** ⇒ 界面**冻住**了（正在生成的那条没重算）；
- 只涨**未命中** ⇒ memo **根本没接上**（其余行每段都被重算）。

用的判据是**库自报的计数**（`memo_hits` / `memo_misses`，§14.1），不是读代码相信 ——
这也正是 §11.2 那次"看起来包了其实没有"教的：**接线必须能被实跑证明**。

```moonbit
@html.div(
  attrs=attrs(@style.Style::new()),
  @moobile.memo_list(model.items, by=item_key, f=t => item_row(t, emit)),
)
```

**键（`item_key`）在这一行上是三样**，每一少的症状都写进了模板的注释 —— 其中第三样最值得看：

| 字段 | 少了它的症状 |
|---|---|
| `text` | 改文案**画不出来** |
| `done` | 勾选状态 / 颜色 / 对钩**停在旧值** |
| `id` | **最隐蔽**：行里的 `emit(Toggle(t.id))` 是**被复用的那份闭包** —— 列表重排/插入之后，同一位置换成另一条**同文案同状态**的待办时，点下去会**切换错的那一条** |

**判据（都实跑）**：

| 门 | 结果 |
|---|---|
| `node tools/template_compare.mjs`（T1：生成物 ↔ `todo-app`，清单外差异即红） | **15 / 0**（`app.mbt` 是"生成物独有"，内容不参与比对 ⇒ **不需要往 `deltas.txt` 加条目**） |
| `node tools/verify_headless.mjs`（模板应用：首屏 + 输入 + 添加 + 勾选 + 删除） | **10 / 0** —— **这四个动作都真的驱动了这个列表** ⇒ `text` / `done` / 位置变化这三条键都被端到端走到了 |
| `node tools/template_check.mjs`（生成 → 编译 → 无头跑起来） | **15 / 0** |
| `bash tools/verify_all.sh` | **25 / 0**（这一轮**没有**新增门条目 —— 上面那三条判据本来就在门里） |

**那个"没自动化测试"的缺口，本轮补上了 —— 而且做了证伪**（这是本节最值得看的一段）：

`tools/verify_headless.mjs` 新增一段剧本（模板与 demo 通用；行的形状不匹配就 **SKIP**，不假装验过）：

> **加两条同名待办 → 删掉第一条 → 勾剩下的那条 → 断言它勾的是它自己。**

| 跑法 | 结果 |
|---|---|
| 正常（键里有 `id`） | **13 / 0**（原 10 项 + 这 3 项） |
| **证伪**：把 `id` 从 `item_key` 里临时拿掉、重编再跑 | 那条**准确变红**，报 `点过之后 text=""` —— 即"命中缓存 ⇒ handler 还指向已删的 id ⇒ **点不动**"，**与上面预测的失败模式逐字一致** |

⇒ 这条契约从此**有测试守着**（不再只靠注释）。顺带把一条方法论摆在这里：
**"能红的测试"才算判据** —— 一条永远绿的断言，与没有断言的区别只是字数。

### 14.9 把"只有 memo 用得上"的记账从**所有人的每帧**上移走（本轮，P3 最后一块）

**问题**：`MCtx` 的路径记账（每个孩子一次 `enter`/`leave`）**只有 `VNode::Thunk` 用得上**，
但它是**每帧每个元素**都要付的。§14.5 的含时归因里，`render_memo` + `render_children_memo` 自身
≈ **14.6%**，而改造前的 `render_node` + `render_children` 只有 ≈ **6.3%** ⇒ 大约 **8% 是记账税**
（还多一层：memo 路上非 thunk 孩子要经 `render_node` 二次派发）。

**做法**（`render.mbt`）：先走**不记账的快路**；一旦真的遇到 thunk，就把**这一帧作废**、
`armed = true`、改用记账路重画。此后一直走记账路。

```
armed = false → 快路（零记账）
   ├─ 全程没 thunk ⇒ 就这么交了（不付一分记账）
   └─ 见到 thunk   ⇒ 作废 + armed = true + 重画这一帧（**只发生一次**）
armed = true  → 记账路（与从前逐字一致）
```

⚠️ **这里的关键是"不做猜"**：不是根据上一次的形状猜"这次有没有 thunk"，
而是**真的走一遍、遇到就是遇到**。所以不存在"换了屏之后 memo 静默失效"那种失败模式 ——
那正是这类优化最容易踩的坑（省下记账、赔掉功能）。重画安全，因为 `render_*` **只有建对象这一个副作用**。

| N=1000 · 12 轮交错 | min | 中位 | 均值 | p95 |
|---|---|---|---|---|
| `translate` | **−29.7%（不重叠 ✅）** | **−22.1% ✅** | **−33.3% ✅** | **−41.1% ✅** |
| `dom` | −15.8%（重叠 ⚠️） | −15.9% ⚠️ | −15.0% ⚠️ | −12.3% ⚠️ |

比估的 8% 大：记账之外，memo 路上还有**二次派发**（非 thunk 孩子要走 `render_node`）—— 快路只有一层。

**正确性（这次改动唯一真正的风险面）**，四条判据都实跑：

| 判据 | 结果 |
|---|---|
| `perf_bench --memo` 档 | 形状 **7** ✓、**命中 1000/帧 · 未命中 0** ✓（说明"武装"确实发生且 memo 真的在工作） |
| chat-app 无头（真应用流式） | **23 / 23**，那条端到端断言仍报 **命中 +4 · 未命中 +4** ✓ |
| 模板无头（含"同名两条"那条记忆化剧本） | **13 / 13** ✓ |
| `bash tools/verify_all.sh` | **25 / 0** ✓ |
