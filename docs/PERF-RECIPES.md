# 性能配方 —— 写应用时要做的三件事（**给用 moobile 写应用的人**）

> 这份文件回答一个问题：**"我这页为什么卡，以及怎么改。"**
> 归因、基线、仪器与全部数字在 [`PERF.md`](PERF.md)（那是给改库的人看的）；
> 这里只放**应用侧能动手的部分**，每条都带**可自查的判据**。

---

## 0. 一句话

**每帧重建的东西越少，越流畅。** moobile 把"哪些东西没变"这件事**交给应用声明** ——
因为只有应用知道。库负责把它兑现（[`memo`](#1-长列表包-memo最值钱的一条)）。

---

## 1. 长列表：包 `memo`（**最值钱的一条**）

```moonbit
fn view(model : Model, emit : @cmd.Emit[Msg]) -> @html.Html {
  @html.div(
    @moobile.memo_list(
      model.rows,
      by=row => row.id,                 // ← 键：**必须完备**（见下）
      f=row => row_html(row, emit),
    ),
  )
}
```

改之前那一列是 `model.rows.map(row => row_html(row, emit))`，改之后是上面这几行。

**值多少**（N=1000 行，本机；见 [`PERF.md` §13.4](PERF.md)）：

| 每帧只改表头（`memo` 命中） | 改前 | 改后 |
|---|---|---|
| 翻译层 | 3.548 ms | **0.090 ms（−97.5%）** |
| 整条 Web 帧（React + jsdom） | 10.29 ms | **0.32 ms（−96.9%）** |

> ⚠️ 那是**上界**（每帧只有表头在变）。真实应用每帧改的更多、命中的更少 ——
> 可迁移的是机制，不是这个百分比。

> ✅ **新项目不用自己加**：`moobile-host init` 生成的最小 Todo 里，列表已经这么写了
> （`examples/apps/template/app.mbt` 的 `memo_list` + `item_key`）—— 照着它改就行。

**行的渲染依赖"第几条"时**（最后一条要画光标、交替行色…）用带序号的版本：

```moonbit
@moobile.memo_list_i(
  model.bubbles,
  by=(i, b) => bubble_key(b, sending && i == n - 1),
  f=(i, b) => bubble_row(b, sending && i == n - 1),
)
```

⚠️ **序号一旦进了 `f`，就必须进 `by`** —— 否则"第几条挪了位置、内容却没重算"，
症状是**画面停在旧内容上**。

⚠️ 同理，**行里的 handler 捕获了什么，什么就得进键**：`emit(Remove(t.id))` 这种写法意味着
`id` 必须在键里 —— 否则"删掉一条、同一位置换成另一条同文案同状态的行"之后，
被复用的那份闭包仍然指向**已经删掉的 id** ⇒ **点下去没反应**（界面看起来一切正常）。
这条有测试守着：`tools/verify_headless.mjs` 里那段"同名两条 → 删第一条 → 勾剩下那条"。

真实例子就见 [`../examples/apps/chat-app/app.mbt`](../examples/apps/chat-app/app.mbt)（流式气泡列表）：
它的无头判据里有一条**端到端**的断言 —— 流的每一段 **命中 +N / 未命中 +1**，
两个数都要涨（只涨命中 = 界面冻住；只涨未命中 = memo 没接上）。

### 键的契约（**错了会画出旧内容**，比"没省下时间"严重）

`memo` 的契约是：**键相同必须蕴含"这一行的 HTML 与 handler 等价"**。

1. **键要把这行的渲染依赖都装进去**：`id` / 文案 / 高亮 / 选中态 / 任何影响长相的东西。
   只按 `id` 取键、而行里还有个 `hot` 会变 ⇒ **那行的变化永远画不出来**。
2. **别用"第几行"当键**。在列表头部插一行，所有位置整体错位 ⇒ 静默错配。
3. 行里的 handler 也是被复用的那一份 —— 它捕获的东西若会变，同样要进键。

### 自查（**别靠读代码相信**）

`memo` 的失败模式是"看起来包了、其实没有"。库提供两个诊断计数，任何宿主里都能读：

```js
globalThis.__moobileApp.memo_hits();    // 命中次数
globalThis.__moobileApp.memo_misses();  // 未命中次数
```

**判据**：每帧稳定发生 **命中 ≈ 行数**、**未命中 ≈ 0**。若命中也稳定为 0 ⇒
键每帧都在变（或者列表根本没走 `memo`）。

> 基准仪器已经把这两个数印在每一份读数里（`memo 命中 X/帧`），
> 并且在"开了 memo 却零命中"时**直接报错**，免得引用一份什么都没量到的数字。
>
> **你自己的应用**也有现成的一条：`node tools/verify_headless.mjs --app <你的应用>` 跑完会打一行
> `备忘录（诊断，不判红）：memo 命中 X · 未命中 Y` —— **命中为 0 就是「一个列表都没包」**。
> （它刻意不判红：行数少、每帧全变的列表包了也白搭 —— 这条是**点名**，不是及格线。）

## 2. 虚拟化：长到几百行以上时，`memo` 之外还要考虑"只渲染可见的"

`memo` 解决"**没变的不重算**"，不解决"**变了的一次算太多**"。
1000 行的非虚拟化列表，即使每行都命中，React 仍要走一遍孩子链表；
真机上更贵的是**布局与绘制**（那一层本仓库的离线仪器根本量不到，见 `PERF.md` §9）。

**判据**：屏幕上同时可见的行如果只有十几行，那就别做 1000 行的列表 ——
用 `FlatList` 一类的虚拟化容器，把"每帧的元素数"从 N 降到"可见行数"。

---

## 3. `update` 里别重建整个世界

`memo` 的命中率取决于"键有没有变"。如果 `update` 每帧都 `rows.map(...)` 重建全部行对象，
而键是按**结构相等**（`id`）取的，那仍然会命中（键值相同）——**但如果键是按引用/时间戳取的，就永远命不中**。

**判据**：键只取"会改变这一行长相"的字段值，不要取"这一帧的编号"或整个对象的哈希。

## 4. 样式：用类型化的 `Style`，别在 `view` 里拼字符串

```moonbit
@html.div(attrs=@html.Attrs::build().styles(@style.Style::new().flex(1.0).color("#1a1410")))
```

理由不是风格，是**成本**：样式表在每帧每元素上都要走一遍，
字符串通道（`style="..."`）会让它变成解析 + 拼接（而且 RN 那边根本不认）。见 `PERF.md` §13。

## 5. 三条"别做"

| 别做 | 为什么 |
|---|---|
| 在 `view` 里做 I/O、计时器、日志 | `view` 每帧都跑；副作用会**按帧**发生 |
| 用行号/索引当 `memo` 的键 | 见 §1 —— 静默画旧内容 |
| 拿"每帧元素数"当唯一判据 | 它只是**中间量**：真正要看的是帧时间（`PERF.md` §10 纪律 14） |

## 6. 出问题时先量什么

| 症状 | 先看 |
|---|---|
| 列表滚动卡 | 是否包了 `memo_list`？`memo_hits` 每帧是否 ≈ 行数 |
| 改了一行但界面不变 | 键是不是没包含那个字段（§1 的契约） |
| 首屏慢 | 首帧元素数（是不是一次渲染了太多行 → §2） |
| 拿不准 | `node tools/perf_bench.mjs --n 1000 --mode dom`（需要仓库；它量的是负载，不是你的应用） |
