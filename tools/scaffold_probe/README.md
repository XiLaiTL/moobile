# scaffold_probe —— "生成出来的项目撑不撑得住一个像样应用"

`tools/scaffold_probe.mjs` 是门，这里放的是**喂给它的应用源码**。

## 它做什么

```
moobile-host init 生成一个项目  →  把 app/ 里的三份 .mbt 覆盖上去  →  moon check/build
                                →  moobile-host build  →  无头跑一遍（含多页面与过滤）
```

## 为什么它住在 `tools/`，而不是 `examples/apps/`

与 `tools/pub_probe/`、`tools/ext_probe/` 同一条规矩：**只为一条门存在、不打算给人跑** ——
它没有 README、没有宿主配置、没有 `moon.mod`，就是几个等着被拷进别人工程的 `.mbt` 文件。

真给人跑的示例是 `examples/apps/todo-app/`（那份要验的是"能力全不全"，包含本地库与网络）。

## 它验的是什么（设计上刻意与模板不同）

| 与模板的差异 | 为什么要有 |
|---|---|
| 拆成三个文件（`app.mbt` / `model.mbt` / `ui.mbt`） | 模板是单文件；应用一大就会拆，而"拆了还编得过、跑得起来"没人验过 |
| 多一个**编辑页**（`Page::Edit`） | 页面切换是 `view` 上的一条分发，最容易在"生成物 + 多文件"下出问题 |
| **过滤**（全部 / 未完成 / 已完成） | 同一个 Model 的另一种读法，验"列表是从状态算出来的"而不是缓存 |
| 删除按钮写 `✕`（模板是 `删`） | 无头验证的剧本按**文字**找按钮，这条差异正是"剧本不能写死一套文案"的证明 |

## 它**不**验什么

能力（本地库 / 网络）、样式、真机手势 —— 各有更合适的门（`todo-app` 的 e2e、
`tools/verify_android.py`）。这里要回答的只有一个问题：**脚手架生成出来的形状，能不能承载真应用。**
